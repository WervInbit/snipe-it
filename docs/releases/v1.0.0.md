# Inbit Device Refurbishment Platform V1.0.0

V1.0.0 retrospectively designates the exact internal production baseline
deployed on 2026-09-01. The repository owner accepted this baseline on
2026-09-03 so subsequent fixes, tests, documentation, and feature additions can
continue as post-V1 work.

This is an internal operational release, not a generally supported public
distribution. The deployed application retained its earlier
`v0.9.0-dev` embedded display metadata; the immutable Git tag, source commit,
and image digests below are the authoritative V1.0.0 identity.

## Product

V1 turns the inherited Snipe-IT inventory foundation into an Inbit-focused
device-refurbishment platform. It covers intake and scan-first lookup, device
and model-number specifications, component traceability, ordered workflow
profiles and items, controlled evidence, work orders, role-based product setup,
and sale-readiness decisions.

This fork is not operationally interchangeable with upstream Snipe-IT. Its
supported deployment, upgrade, permission, workflow, and data contracts are
defined by this repository.

## Main V1 Capabilities

- Explicit device lifecycle statuses replace the legacy checkout/checkin/audit
  mutation flow for refurbishment work.
- Models, exact model-number presets, structured attributes, expected
  components, installed component hierarchy, condition, and lifecycle history
  describe the physical device.
- Ordered Workflow Profiles and Workflow Items support diagnostics and tasks,
  resumable runs, requiredness snapshots, controlled evidence, and current
  sale-readiness evaluation.
- Refurbisher, Senior Refurbisher, Supervisor, and Admin roles use an additive
  least-privilege permission model. Supervisor can perform ordinary product and
  workflow setup; destructive catalog lifecycle controls remain Admin-only.
- License keys and license/private-file operations are gated independently from
  ordinary asset visibility.
- Public gallery media is separated from private files and workflow evidence.
- A production foundation seeder is separated from destructive demo/scenario
  data, and production catalog seeding fails closed for unverified identifiers.
- Production containers use immutable app/web images, external file-backed
  secrets, durable upload/backup storage, dedicated queue/scheduler services,
  and explicit health checks. Reusable repository-managed MariaDB/Redis, TLS
  edge, and loopback registry overlays were added after the V1 source commit.

## Supported V1 Boundary

- PHP 8.2 and Laravel 11.
- MariaDB/MySQL; MariaDB 11.4.7 is the exact populated rehearsal engine.
- Redis for production cache, sessions, queues, and shared maintenance state.
- Docker Compose v2 using the repository production profile and selected
  reviewed overlays.
- Local user/password authentication and the documented two-factor behavior.
- LDAP login/synchronization and outgoing SMTP delivery are disabled and
  unsupported in V1.
- PostgreSQL production deployment is outside the V1 support matrix.
- PHPStan is not a V1 release gate.

## Upgrade And Data Preservation

Upgrade the complete database and matching public/private uploads; do not
recreate production users through CSV or seeders. Preserve the existing APP key
and Passport keys. Existing password hashes, user/group relationships, history,
and operational records are migrated in place.

Use the controlled maintenance, backup, migration, additive permission seeder,
health, acceptance, and rollback sequence in
[`docs/production-deployment.md`](../production-deployment.md). Never use the
inherited upstream installer/upgrader or destructive migration/reset commands
on retained data.

## Known V1 Limitations

- No real LDAP or SMTP integration support.
- The current QR layouts ship as-is; a printer/DPI/sticker designer is post-V1.
- Windows installation automation, battery-health and SMART diagnostics, and
  automated result ingestion are post-V1.
- Private attachments/evidence are not a credential vault. Do not store
  passwords, recovery codes, or customer/repair credentials in them.
- Asset gallery images are public catalog/device media.
- Migration history is retained for upgrades; a fresh-install migration
  snapshot/squash is post-V1.
- Five unused demo placeholder model-number rows may exist in upgraded legacy
  databases. New production seeding excludes them; operators may explicitly
  deprecate or replace them after identifying the actual hardware.
