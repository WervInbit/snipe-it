## Action And Choice Structure

- Page 1 selects A-H; other route pages are not follow-up tasks.
- A/page 2: Active/Deprecated code. B/page 3: default selection A OR unused-code removal B.
- C/page 4: remove direct attribute OR expected-component row, then save/reopen/inspect affected assets.
- D/page 5: hide/restore the whole attribute. E/page 6: maintain one saved Enum option.
- F/page 7: activate/deactivate a reusable component definition. G/page 8: remove a saved child OR contribution, then Save Changes.
- H/page 9: retain or change an in-use numeric aggregation rule after impact checks, then compare real affected examples.

## Operating Contract And Boundaries

- Keep the registered title Bestaande catalogus aanpassen. Normal creation stays in CAT-01/02/03/04; uncertain source facts go to CAT-06.
- Primary cannot be deprecated/deleted. Select another valid active code of the same Basismodel first. A deprecated row is saved Active and reopened before the default checkbox.
- Unused-code deletion requires Assets = 0, not Primary, known specification/images/history impact and a certain target despite the generic confirmation. No action is taken when the visible removal route is absent.
- Removing a direct attribute also deletes associated overrides for that model number. Inspect every affected asset's Specification/Override and preserve its identity and old value; incomplete impact defers removal. Re-adding the attribute does not restore old overrides automatically.
- Expected-row removal changes catalogue expectations, not physical Tracked inventory. Preserve quantity, required state and derived child/attribute outcomes.
- Hide/Unhide and definition Activate/Deactivate act directly. Browser definition-delete routes do not exist. Counts are not per-option usage proof and Templates does not enumerate child relations.
- For a saved Enum row distinguish Value from Label. Active controls new choice availability; Remove requires known unused impact and Save. Existing records can change and an automatic usage guard is not assumed.
- Child/contribution Remove is local staging until Save Changes. Remove only the intended relationship and inspect affected model/asset results.
- In-use Sum versus distinct changes existing results. Record the old rule/examples, inspect sources/children/quantities/flags and change only when meaning requires it. A correct existing Sum can remain; unexpected results require restoring/checking the old rule and investigation.
- Each indexed task can use local action numbers; alternatives within it must be labelled explicitly. Routine impact checks are not blanket red STOP banners.

## Revision Reasoning

Required alignment: Current lifecycle controls and a distinct owning route for in-use numeric aggregation.

Chosen improvement: An A-H index separates independent tasks; both code and specification/relationship alternatives are explicit before acting.

Preserve: Existing eight-page maintenance coverage, impact checks, saved verification and no browser definition Delete.

Placement and tradeoff: Nine pages suit eight independent maintenance jobs. Local numbering is legitimate within a selected route; the new rule is not a compulsory ninth execution step.
